# gpu01 compatibility path

gpu01 is an older host around otherwise supported hardware:

- CentOS 7, kernel `3.10.0-1160.el7.x86_64`, glibc 2.17;
- NVIDIA driver `525.105.17`;
- four NVIDIA A800 80 GB PCIe GPUs (`sm_80`);
- no system Apptainer or Singularity installation.

The GPU is therefore not the compatibility problem. The original failure had
two independent causes: there was no SIF runtime in `PATH`, and binaries run
directly on the host selected CentOS 7's old `libstdc++.so.6`. A container-built
binary failed before `main` with missing `GLIBCXX_3.4.20` and newer symbols.

## User Apptainer

The account uses a relocatable, non-setuid Apptainer 1.3.2 installation at
`$HOME/.local/apptainer`. This mode is viable because the host has
`user.max_user_namespaces=15000`, `unshare -Ur` succeeds, and FUSE,
`squashfuse`, and the `squashfs` filesystem are available. The installation
was produced with Apptainer's official `install-unprivileged.sh` workflow and
the EL7 packages mirrored by AlmaLinux.

Runtime state is kept out of the shared home filesystem where possible:

```sh
export APPTAINER_CACHEDIR="$HOME/.cache/evo.cpp/apptainer"
export APPTAINER_TMPDIR="/tmp/evo.cpp-apptainer-$UID"
```

The existing CUDA 12.8/Rocky 8 SIF was successfully mounted by this user
installation. `apptainer exec --nv` exposed all four A800s, and the existing
CUDA 12.8 smoke binary passed device discovery, `cudaMalloc`, a real `sm_80`
kernel launch, cuBLASLt handle creation, and cuFFT plan creation on driver
525.105.17. This is consistent with NVIDIA's CUDA 12.x minor-version
compatibility floor of driver 525, but it does not prove that every CUDA 12.8
feature is available on that driver.

## Proven CUDA 12.8 build

The default gpu01 path uses
[`evo.cpp-cuda12.8-rocky8.def`](../containers/evo.cpp-cuda12.8-rocky8.def)
and the user Apptainer runtime. CUDA 12.x minor-version compatibility allows
this on a 525-series driver, and this exact combination has passed real kernel,
cuBLASLt, cuFFT, and current-source CUDA operator tests on gpu01:

```sh
scripts/gpu01_build.sh
```

The script syncs only source files, requires a prebuilt
`$HOME/evo.cpp-cuda12.8-rocky8.sif`, configures a separate
`build-gpu01-cu128`, builds for `sm_80`, and runs both the CUDA smoke and CUDA
operator suites.

The complete gpu-labeled CTest pass also succeeded on gpu01: `cuda_smoke`,
`cuda_ops`, `fp8_sass`, `cuda_hyena`, `cuda_attention`, `cuda_model`,
`cuda_pipeline`, and `cuda_cli`. The optional external Triton oracle was
unavailable and reported a skip rather than a pass.

The current-source build was also checked against the fixed raw-bit CUDA 12.8
evidence on driver 525.105.17. For the 128-token `vortex_length128` prefill,
the complete logits NPY was byte-identical on gpu01, with SHA256
`8ab758202a61e93bdcfa77dc74c34aed9bc6dee405eb2e9a6056f08aa03ce46c`.
For four cached generation steps, all 52 native reference NPY files and the
generated bytes were byte-identical. This comparison used the matching input;
the similarly sized `deterministic_128` benchmark is a different sequence and
must not be compared to the `vortex_length128` evidence.

## Optional CUDA 12.4 image

For a stricter toolkit ceiling, set `EVO_GPU01_CUDA_RELEASE=12.4` after building
[`evo.cpp-cuda12.4-rocky8.def`](../containers/evo.cpp-cuda12.4-rocky8.def).
The SIF should be built on a registry-connected host; gpu01 cannot currently
pull OCI layers reliably. If
`$HOME/.cache/evo.cpp/cuda12.4.1-devel-rockylinux8-amd64.docker.tar` exists,
the image script imports that offline Docker archive instead of contacting the
registry. On this cluster, gpu01 and gpu02 share the same home filesystem, so
the complete workflow is:

```sh
scripts/gpu01_build_image.sh  # builds CUDA 12.4 SIF on gpu02
EVO_GPU01_CUDA_RELEASE=12.4 scripts/gpu01_build.sh
```

## Exactness boundary

Container startup and CUDA operator tests are compatibility gates, not complete
model-level numerical evidence. The targeted gpu01 CUDA 12.8 raw-bit checks
above cover the two principal prefill and cached-generation paths, while the
full boundary matrix remains documented in the 7B exactness audit. Any new
toolkit path, including CUDA 12.4, must rerun the complete raw-bit prefill and
cached-generation suite. A CUDA 12.4 build must not be described as exact only
because it compiles, launches kernels, or produces high cosine similarity.
